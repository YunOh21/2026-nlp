# Project 1 — 숫자·영어·한국어 번역 (doyeon)

숫자, 영어, 한국어 수 표현을 서로 번역하는 Seq2Seq 모델입니다. GRU Encoder–Decoder에 Attention을 붙였고, 출력은 Greedy decoding으로 만듭니다. 6방향을 모델 하나로 처리합니다.

영어↔한국어는 원본 데이터에 짝이 적어서 긴 숫자를 잘 번역하지 못했습니다. 그래서 학습한 모델로 빠진 짝을 만들어(생성 짝) 다시 학습했고, 10자리까지 직접 번역이 99.8% 이상 나왔습니다.

## 파일

```text
practice01/doyeon/
├── README.md
├── requirements.txt
├── num2text.ipynb          # 전체 코드와 학습·평가 출력, 마지막 셀에서 모델 로드·테스트
├── pseudo_augmented.pt     # 최종 모델
├── baseline.pt             # 비교용: 원본 데이터만 학습
├── baseline_continued.pt   # 비교용: 원본 데이터로 같은 양만큼 더 학습
├── extra_eval.py           # 긴 숫자 영어↔한국어 추가 평가
├── data/                   # 제공 데이터 num2txt.txt, num2kor.txt
└── results/                # 데이터 분할, test 결과, 추가 평가 결과
```

## 실행

```bash
pip install -r requirements.txt
```

`num2text.ipynb`를 이 폴더에서 엽니다.

- 저장된 모델로 테스트: 첫 번째 코드 셀을 실행한 뒤 마지막 셀을 실행합니다. CPU에서도 몇 초면 됩니다.
- 다시 학습: 모든 셀을 순서대로 실행합니다. 세 모델을 학습해 `.pt`를 덮어씁니다. RTX 4080에서 약 7분 걸렸습니다.
- 추가 평가: `python extra_eval.py`

마지막 셀 실행 후에는 이렇게 쓸 수 있습니다. 숫자도 문자열로 넣습니다.

```python
translate("12345", "num", "ko")   # '만 이천삼백사십오'
translate("만 이천삼백사십오", "ko", "en")   # 'twelve thousand three hundred forty five'
```

언어 코드는 `num`, `en`, `ko`입니다.

## 방법

- 숫자는 정수로 바꾸지 않고 한 글자씩 토큰으로 넣습니다. 한국어도 글자 단위, 영어는 단어 단위입니다.
- 입력 앞에 `<to_ko>`, `<to_en>`, `<to_num>` 토큰을 붙여 번역 방향을 알려 줍니다.
- 인코더 GRU가 입력을 읽고, 디코더 GRU가 Attention으로 입력을 다시 보면서 한 토큰씩 출력합니다.
- 데이터는 숫자 단위로 train/validation/test(약 8:1:1)로 나눠서, 같은 숫자가 학습과 평가에 같이 들어가지 않게 했습니다.

| 설정 | 값 |
|---|---|
| 임베딩 / 은닉 크기 | 128 / 256 (GRU 1층) |
| 파라미터 수 | 749,249 |
| 배치 / 학습률 | 512 / 0.001 (Adam) |
| 학습 epoch | baseline 20, 추가 학습 8 |
| 모델 선택 | validation 완전일치율이 가장 높은 epoch |

## 영어↔한국어 생성 짝

영어 파일과 한국어 파일에 같이 있는 숫자는 12,738개뿐이고 9·10자리는 없습니다. 그래서 train의 영어↔한국어 짝은 10,188개밖에 안 됩니다.

train 숫자 중 영어나 한국어 한쪽만 있는 139,620개를 골라 baseline 모델로 빠진 쪽을 번역했습니다. 확신도(토큰 확률 평균)가 0.9 이상이고, 다시 숫자로 번역했을 때 원래 숫자가 나오는 것만 남겼습니다. 이렇게 278,992개 짝을 추가하고 손실 가중치 0.5로 8 epoch 더 학습했습니다. validation·test 숫자는 쓰지 않았습니다.

학습량이 늘어서 좋아진 건지 확인하려고, 원본 데이터만으로 같은 횟수만큼 더 학습한 `baseline_continued`도 만들었습니다.

0.9, 0.5, 8 epoch는 미리 정한 값이고 따로 조정하지 않았습니다.

## 결과

### 원본 test

| 방향 | 문제 수 | baseline | continued | augmented |
|---|---:|---:|---:|---:|
| 숫자 → 영어 | 10,001 | 99.95% | 99.97% | 99.94% |
| 숫자 → 한국어 | 10,001 | 99.92% | 99.97% | 99.91% |
| 영어 → 숫자 | 10,001 | 99.94% | 99.97% | 99.89% |
| 한국어 → 숫자 | 10,001 | 99.97% | 99.98% | 99.85% |
| 영어 → 한국어 | 1,275 | 99.69% | 99.76% | 100.00% |
| 한국어 → 영어 | 1,275 | 99.84% | 99.92% | 100.00% |

원본 test의 영어↔한국어는 8자리 이하뿐이라 세 모델 차이가 거의 없습니다. augmented는 숫자 쪽에서 조금 더 틀렸습니다(한국어→숫자 13문제).

### 긴 숫자 영어↔한국어 (`extra_eval.py`)

test 숫자 18,727개 전체로 다시 평가했습니다. 원본에 없는 쪽 정답은 수 읽기 규칙으로 만들었습니다. 이 규칙은 원본 20만 줄과 모두 일치하고, 채점에만 썼습니다(학습과 모델 선택에는 쓰지 않음). 직접 번역과, 같은 모델로 숫자를 거치는 번역(영어→숫자→한국어)을 같이 쟀습니다.

영어 → 한국어

| 자릿수 | baseline 직접 | baseline 숫자 경유 | augmented 직접 |
|---:|---:|---:|---:|
| 5 | 99.93% | 99.96% | 99.96% |
| 6 | 96.60% | 100.00% | 100.00% |
| 7 | 57.96% | 99.90% | 100.00% |
| 8 | 0.00% | 99.87% | 99.87% |
| 9 | 0.00% | 99.80% | 99.83% |
| 10 | 0.00% | 99.80% | 99.90% |

한국어→영어도 비슷합니다. baseline 직접은 7자리 71.77%, 8자리부터 0%이고, augmented 직접은 모든 자릿수에서 99.9% 이상입니다. 전체 결과는 `results/extra_eval_metrics.csv`에 있습니다.

원본만 학습한 모델은 7자리부터 직접 번역이 무너집니다. 같은 양을 더 학습한 continued도 마찬가지라, 학습량 문제는 아닙니다. 숫자를 거치면 baseline도 99.8% 이상 나오는데, 생성 짝으로 학습한 모델은 숫자를 거치지 않고 직접 번역해서 같은 수준이 나왔습니다.

## 한계

- validation에는 원본 정답만 넣어서 9·10자리 영어↔한국어가 없습니다. 그래서 모델을 고를 때 긴 숫자 성능은 반영되지 않았고, 학습이 끝난 뒤 따로 확인했습니다. 규칙 정답을 validation에 넣으면 규칙이 모델 선택에 관여하게 되어 넣지 않았습니다.
- `1000000`, `1000000000`처럼 0이 길게 이어지는 숫자는 대부분 틀립니다(13개 숫자 × 6방향 중 6개 정답). 데이터에 끝자리 0이 5개 이상인 숫자가 없습니다.
- 시드 하나로 한 번 실행한 결과입니다.
